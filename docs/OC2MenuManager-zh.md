# OC2MenuManager 使用说明

英文版： [OC2MenuManager.md](./OC2MenuManager.md)

## 简介

`OC2MenuManager` 是一个独立的 Overcooked! 2 菜单辅助模组。
它不依赖 `ConfigurationManager.dll` 或 `HostUtilities`。
它有自己的游戏内配置窗口。
如果安装了 `OC2DIYLevel` 或 Recipe Extension（`OC2ManyRecipes`），模组会通过受保护的可选适配器加入这些菜品，但不会把它们变成必装前置。

当前主要功能：

- 按关卡追踪菜品
- 左侧历史菜单悬浮窗
- 已备菜品识别
- 顶部真实菜单卡片上色
- 顶部额外猜单显示
- 麻团关卡相关菜单辅助
- 内置无菜单开关

## 前置条件

- `Overcooked! 2`
- `BepInEx`

当前兼容目标是 Steam build `20236421`。维护者可用下面的命令核验参考清单/哈希，并对该精确版本编译；完整游戏 DLL 不会复制进仓库：

```powershell
.\tools\Test-BaseGameCompatibility.ps1 -ReferenceRoot 'C:\path\to\Overcooked2-BaseGame\build-20236421'
```

## 可选模组兼容性

- 支持 `OC2DIYLevel` 0.8 风格以及新版的菜谱接口。
  - DIY 前端元数据加载完成后，模组会读取关卡及其准确的菜谱 ID/名称。
  - 不用先进入关卡，就能选择 DIY 关卡并配置追踪菜品。
  - 原版 DIY 菜谱可在前端完整读取；自定义菜谱会先按 ID/名称预载，开局后再升级成真实运行时定义。
- 支持 Recipe Extension / `OC2ManyRecipes` 1.1 的运行时菜谱。
  - 扩展模组在服务端/客户端本局同步期间生成菜谱后，菜单管理器会自动并入当前关卡。选择器和局内悬浮窗按菜谱 ID 各显示一行；同名菜会保留 ID 以便区分。
  - 某关卡没有保存过子集时，新生成 ID 会自动追踪；一旦保存过明确子集，之后发现的新 ID 默认不勾选。关闭扩展只会移除本局的扩展专属行，不会删除已保存 ID。
  - 概率计算会保留提供方顺序和重复条目。如果已启用提供方的快照不完整，或运行时频率数组形状不一致，概率会显示 `—`、不生成猜单，并安全关闭本局无菜单。
  - 保留扩展模组两个特殊动态关卡的阶段筛选规则。
  - 真实订单始终保留自己的位置；只要关卡本身不超过 10 张真实订单，活动中的真实订单和猜单总数就不会超过 10。
  - 即使其他模组之前给真实订单分配了无效的 UI 桌号，成功交付后也会正常播放移除动画并销毁。订单过期则遵循原版：同一张订单保留并重置计时。
  - 在麻团关卡中，非固定的“好菜单/好蛋糕”会使用 Recipe Extension 的完整菜谱池，但特殊限制只作用于原版麻团菜谱；固定/TAS 菜单仍只使用原版固定序列。

这两个兼容项都是可选的。Menu Manager 不会引用、打包或修改提供方 DLL，也不会修改其设置或集合。如果可选模组未安装，或未来版本不再提供已知反射接口，只会关闭对应兼容项，菜单管理器的独立功能仍会继续运行。私密联机中双方都安装并启用 Recipe Extension 时可继续追踪；远端概率有歧义时仍显示 `—`。公开联机遵循 Recipe Extension 自己的禁用行为；部落（Horde）仍不属于 Menu Manager 追踪和无菜单范围。

## 安装方法

最小安装：

1. 把 `OC2MenuManager.dll` 复制到以下任意位置：
   - `Overcooked! 2\BepInEx\plugins\`
   - `Overcooked! 2\BepInEx\plugins\OC2MenuManager\`
2. 启动游戏。

可选文件：

- `OC2MenuManager.pdb`
  - 不是必需文件
  - 只用于调试

## 模组会使用哪些文件

插件文件：

- `Overcooked! 2\BepInEx\plugins\OC2MenuManager\OC2MenuManager.dll`

主配置文件：

- `Overcooked! 2\BepInEx\config\OC2MenuManager.standalone.cfg`

热键文件：

- `Overcooked! 2\BepInEx\config\OC2MenuManager.hotkey.txt`

菜品追踪选择文件：

- `Overcooked! 2\BepInEx\config\OC2MenuManager.selections.txt`

可选的菜品发现报告：

- `Overcooked! 2\BepInEx\config\OC2MenuManager.dish-catalog-report.txt`

如果新选择文件不存在，模组会从旧的 `HostUtilities-ServedDishTrackerSelections.txt` 复制一次数据；旧文件不会被删除或覆盖。

## 如何打开配置窗口

默认热键：

- `F6`

热键保存在：

- `BepInEx\config\OC2MenuManager.hotkey.txt`

示例内容：

```txt
# OC2MenuManager hotkey config
# Edit the value after Hotkey= and save the file.
# Use Hotkey=None if you want to disable the launch hotkey.
Hotkey=F6
```

常见写法：

- `Hotkey=F6`
- `Hotkey=F7`
- `Hotkey=Home`
- `Hotkey=None`

改热键有两种方式：

- 在模组窗口里点击热键行直接改
- 直接编辑 `OC2MenuManager.hotkey.txt`

## 推荐的首次使用流程

1. 按 `F6` 打开模组窗口。
2. 在 `菜单追踪` 里选择关卡。
3. 勾选你要追踪的菜品。
4. 打开 `启用菜单追踪`。
5. 如果你想显示左侧面板，打开 `显示悬浮窗`；它默认关闭。
6. 如果你想在顶部额外显示猜单，调整 `最大猜单数量`。
7. 如果你想识别已备成品，打开 `启用已备跟踪`。
8. 如果你想给顶部真实菜单卡片上色，打开 `菜单颜色`。
9. 在 `悬浮窗` 中调整高级位置、尺寸和字体设置，让面板适合你的屏幕。

## 当前配置窗口分区

当前窗口包含这些分区：

- `菜单追踪`
- `历史菜单追踪`
- `层级设置`
- `功能开关`
- `悬浮窗`
- `界面`

### 菜单追踪

这一组决定模组当前允许追踪哪些菜。

你可以在这里：

- 选择关卡
- 按关卡 ID、中文元数据名称或英文元数据名称搜索
- 勾选当前关卡要追踪的菜品
- 使用按类别生成的快捷按钮，比如蛋糕、汉堡、披萨等
- 使用全选、清空、刷新之类的批量操作

关卡选择的当前逻辑：

- 不在关卡内时，可以自由切换关卡
- 在关卡内时，会自动锁定为当前关卡
- 这个锁定只是临时显示本局关卡，不会覆盖你手动配置的关卡；本局结束后会恢复之前的选择
- 展开后会显示“筛选结果 / 总数”和 DIY 数量，并支持滚轮、方向键、Page Up/Down、Home/End 与 Enter
- 后台刷新元数据时会保留滚轮与滚动条位置，不会自动跳回选中项
- 连续配置多个关卡时会保留搜索内容；关闭设置窗口后清空

这个锁定是故意的，目的是避免实战中误切到别的关卡。

OC2DIYLevel 完成前端元数据加载后，DIY 关卡会自动出现。Menu Manager 不会扫描游戏目录、枚举 `levels` 文件夹，也不会自行加载 DIY AssetBundle；它只接受 OC2DIYLevel 已经加载到内存中的权威目录，因此同目录下的截图、文本文件和其他附带文件不会被误认为关卡。临时读取失败时会继续保留上一次有效目录；单个无效或重复元数据条目会被跳过并报告，不会让其他有效关卡一起消失。选择关卡时才会按需读取菜谱；读取失败时，只要窗口保持打开就会自动重试，也可以点击按钮立即重试。现在不需要为了配置而先进入一次 DIY 关卡。

Recipe Extension 的菜谱是在本局初始化时依据真实关卡生成的，因此会在同步完成后自动出现在当前关卡选择列表和局内悬浮窗中。如果刚修改的扩展配置没有出现，请开始新一局并检查 BepInEx 日志里一次性的 `[Compatibility]` 警告；读取失败的活动快照不会被不完整目录替代。

### 历史菜单追踪

这是最核心的一组设置。

#### 启用菜单追踪

- 是历史、概率、已备跟踪、悬浮窗显示条件、菜单颜色和猜单的总开关
- 关闭后麻团功能、无菜单、设置窗口和始终生效的菜单容量安全修复仍会继续工作
- 只修改了界面名称，原有保存值不会变化

#### 显示悬浮窗

- 紧接在 `启用菜单追踪` 下方
- 从未保存过此设置时默认为 `关闭`
- 只控制左侧悬浮窗；关闭后历史记录、已备跟踪、菜单颜色、概率、选择和猜单都会继续工作
- 局内切换会立即生效，并会跨局、跨场景及重启游戏保存

`最大猜单数量` 紧接在这个开关下方，方便随时调整。

#### 启用已备跟踪

- 识别已经完成、但还没交出的菜
- 会影响左侧悬浮窗状态
- 会影响顶部真实菜单卡片颜色
- 也会影响猜单是否继续显示

已备跟踪会尽量识别多种来源，例如：

- 盘子上的完整菜
- 某些容器中的完整菜
- 某些角色手上的完整菜
- 某些 cooker 刚完成的菜

这项功能是模组里比较重的一块。
如果你感觉卡顿，优先尝试先关闭它。

#### 菜单颜色

- 给游戏顶部真实菜单卡片上色
- 关闭时会立即还原现有菜单，重新打开后会在下一次重绘时立即给现有真实单和猜单上色
- 局内重新打开 `启用菜单追踪` 时，也会发现并上色已经显示的真实订单

颜色项包括：

- `在单颜色`
  - 当前真实在单，且还没备好的单
- `已备颜色`
  - 当前真实在单，且已经备好的单
- `猜单颜色`
  - 顶部额外插入的猜单

透明度说明：

- `A` 通道控制整张卡片的透明度
- 不只是背景，整张单都会一起变淡
- 猜单在此基础上还会额外压暗一点，让它看起来更像参考信息

#### 最大猜单数量

这一行紧接在 `显示悬浮窗` 下方，并且只会在设置窗口中出现一次。

范围：

- `0` 到 `5`

默认值：

- `3`

含义：

- `0` 表示关闭顶部猜单
- `1-5` 表示在真实菜单后面最多额外显示多少个猜单

注意：

- 猜单只是参考，不是真实订单
- 真实订单永远在前面，猜单追加在后面
- 活动猜单数量按 `max(0, min(配置上限, 10 - 当前真实订单数))` 自动调整
- 5 张真实订单可显示 5 张猜单，6 张可显示 4 张，8 张可显示 2 张
- 如果关卡本身生成超过 10 张真实订单，所有真实订单仍会显示，猜单则降为 0

#### 显示语言

模式：

- `Auto`
- `English`
- `Chinese`

当前逻辑：

- `Auto` 跟随游戏语言
- 这个设置会同时影响菜名、分类名、配置窗口文字和悬浮窗文字

#### 关卡名称最大长度

- 控制关卡选择按钮和下拉列表里的最大字符数

#### 菜品名称最大长度

- 控制主窗口里追踪菜品列表的最大字符数

### 层级设置

这一组控制分类优先级。

当前逻辑：

- 每个菜品分类都有一个 `1` 到 `6` 的层级
- 数字越小，排序越靠前
- 点击层级按钮会循环切换数值
- `默认` 用来重置单个分类
- `全部重置` 用来重置所有分类

当前界面表现：

- 分类以五列显示
- 这样纵向不会占太多空间

层级会影响：

- 左侧悬浮窗排序
- 顶部猜单排序
- 分类分组逻辑

层级不会影响：

- 游戏真实出单
- 菜谱内容本身

这是一项按分类设置的功能，不是按单道菜设置。

### 功能开关

这一组是一些额外玩法开关。

#### 麻团好菜单

- 第一单没有葱
- 前两单不会出蛋糕

#### 麻团好蛋糕

- 提高麻团关卡里蛋糕相关菜单出现概率

#### 麻团TAS菜单

- 把麻团菜单锁成 TAS 用序列

#### 无菜单

- 设置在下一局边界生效，状态行会显示已启用、待生效或不支持原因
- 支持标准/动态剧情厨房和本地同屏对战厨房
- 只有确认本局没有特殊开局订单后才关闭正常出单
- 接受本局当前有效的菜谱；动态关卡跟随游戏当前阶段
- 支持 DIY 与 Recipe Extension 菜谱
- 注入一张按队伍隔离的临时订单，再由原版交付流程处理回盘、匹配、连击、得分、模式回调与客户端消息
- 启用期间暂停本模组的悬浮窗、已备追踪、菜单上色和猜单
- Boss、教程、生存、部落（Horde）、计时前依赖订单以及所有联机局（公开或私密）都保留正常菜单，并显示原因

### 悬浮窗

这一组保留左侧游戏内文字面板的位置、尺寸、字体、对齐和颜色等高级设置。是否显示面板由 `历史菜单追踪` 顶部的 `显示悬浮窗` 控制。

可调项目：

- `悬浮窗X`
- `悬浮窗Y`
- `悬浮窗宽度`
- `悬浮窗高度`
- `悬浮窗字体大小`
- `悬浮窗关卡名长度`
- `悬浮窗菜名长度`
- `悬浮窗粗体`
- `悬浮窗最大显示菜品数`
- `悬浮窗文本对齐`
- `悬浮窗字体颜色`
- `悬浮窗上单数量颜色`
- `悬浮窗概率颜色`
- `悬浮窗已备颜色`

实用建议：

- 如果文字被截断，优先调大关卡名和菜名长度
- 如果面板太挤，先降低 `悬浮窗最大显示菜品数`
- 如果面板太碍眼，可以移动位置、减小宽度或字体

### 界面

这一组控制模组自己的窗口外观。

包括：

- `MOD的UI字体大小`
  - 独立窗口和悬浮窗共用的基础字号
- `MOD的UI字体颜色`
  - 独立窗口和悬浮窗共用的基础字体颜色
- `打开菜单管理窗口`
  - 用来改设置窗口热键

## 左侧悬浮窗的显示逻辑

左侧悬浮窗是一个紧凑的待办面板。它默认隐藏，只有 `启用菜单追踪` 和 `显示悬浮窗` 都打开时才显示。单独关闭悬浮窗不会清空或暂停任何追踪状态，再次打开时会按当前数据重新构建，不会重置计数。

它会显示：

- 关卡名
- 排序说明
- 图例
- 每道被追踪的菜
- 上单数量
- 下一单出现概率
- 已备数量

其中已备数量只会在 `启用已备跟踪` 时参与显示和判断。
剧情模式仍显示一个区块；本地对战会分别显示“队伍 1”和“队伍 2”的历史与概率，已备数量仍由整个厨房共享。如果无法取得权威出单状态，也无法无歧义地重建，概率会显示为 `—`，并且不会生成猜单。

### 图例说明

未启用已备跟踪时：

- `[   ]在单`
- `[ - ]未备`
- `[ x ]已上`

启用已备跟踪时：

- `[   ]在单`
- `[ - ]未备`
- `[ x ]已上`
- `[ v ]已备`

含义：

- `在单`
  - 当前真实菜单栏上有这道菜，而且还没备好
- `未备`
  - 当前不在真实菜单栏上、也没备好，但下一单仍有正概率出现
- `已上`
  - 当前不在真实菜单栏上，而且下一单概率已经是 `0%`
- `已备`
  - 已经做好了，但还没有成功交出

### 当前排序逻辑

悬浮窗会尽量把现在最值得处理的项目排在前面。

总体优先级：

1. 在单且未备
2. 不在单、未备、且概率大于 `0%`
3. 不在单、未备、且概率等于 `0%`
4. 已备

同类项目内，再继续按这些条件排序：

- 分类层级
- 下一单概率
- 上单数量
- 显示名称

### 当前视觉规则

- 橙色菜名表示在单未备
- 绿色菜名表示已备
- 蓝色数字表示上单数量
- 金色数字表示概率
- `0%` 行会整体变暗，并带删除线

## 顶部猜单的工作方式

猜单会出现在游戏顶部真实菜单卡片区域里，但它本身不是真实订单。

它只是参考信息，复用了游戏自己的菜单卡片 UI。

一条菜会成为猜单，必须同时满足：

- 这道菜被勾选为追踪对象
- 当前不在真实菜单栏上
- 当前没有备好
- 下一单仍有正概率出现

顶部猜单的候选顺序，来自和左侧悬浮窗 `[ - ]未备` 完全相同的排序来源。
也就是说：

- 左侧 `[ - ]未备` 的相对顺序，就是顶部猜单的相对顺序
- 顶部猜单只是这批候选里按数量截取出来的一部分

当前表现：

- 真实订单永远在前面
- 猜单追加在后面
- 新真实订单加入前，会先移除超出 10 张总上限的猜单
- 猜单失效时会消失
- 如果后面还有新的候选，就会补上来

## 语言和菜名命名

这个模组里的英文菜名是专门整理过的，目标是：

- 更接近中文的命名方式
- 尽量分类在前
- 尽量简洁
- 更适合在菜单列表和悬浮窗里快速扫读

例如：

- `Cake: Chocolate`
- `Pancake: Strawberry`
- `Burger: Cheese`

语言设置不仅影响菜名，也会影响分类名和设置窗口文字。

## 文字被截断时怎么调

如果你觉得有些文字太长，被裁掉了，优先调这些项目：

- `关卡名称最大长度`
- `菜品名称最大长度`
- `悬浮窗关卡名长度`
- `悬浮窗菜名长度`

对应位置分别是：

- 主窗口关卡选择按钮和下拉列表
- 主窗口追踪菜品列表
- 悬浮窗标题
- 悬浮窗菜名

## 性能建议

如果你觉得模组有点重，可以先按这个顺序尝试：

1. 关闭 `启用已备跟踪`
2. 关闭 `菜单颜色`
3. 降低 `最大猜单数量`
4. 降低 `悬浮窗最大显示菜品数`

原因：

- 已备菜品匹配仍是最重的可选功能
- 已备维护只会在来源变化、定期清理到期或延迟兜底阶段到期时运行，不会每帧扫描菜谱
- 关卡/控制器查询已缓存，兜底扫描会延迟并拆分到不同帧执行
- 关卡搜索模型只会在搜索词或来源目录变化时重建，展开列表也只绘制当前可见行
- 菜单布局交给游戏本身；只有真实单/猜单成员发生变化时才调整顺序
- 每支队伍的下单概率和悬浮窗排序只会在上单、阶段或规则变化后重建一次，悬浮窗、已备匹配和猜单会共用结果
- Recipe Extension 的有序生成菜谱会在本局同步后反射读取一次并持续复用；扩展与远端概率重建也会复用工作缓冲区，不会在每次刷新时创建临时集合
- 历史追踪关闭且没有待清理状态时，每帧更新只保留热键和发现报告维护后立即返回

## 常见问题

### 热键没反应

先检查：

- `BepInEx\config\OC2MenuManager.hotkey.txt` 是否存在
- 文件里是不是写成了 `Hotkey=None`
- 是否有别的模组占用了同一个按键

### 我替换了 DLL，但游戏里没变化

先检查：

- 你复制的是不是游戏真正启动目录下的 `BepInEx\plugins`
- 复制 DLL 前游戏有没有彻底退出
- 是否还有别的 `OC2MenuManager.dll` 副本

最稳妥的流程：

1. 完全关闭游戏
2. 确认安装路径
3. 替换 DLL
4. 重启游戏

### 为什么关卡选择被锁住了

这是正常现象。
当你已经进入关卡时，模组会自动锁定到本局关卡。
本局结束后锁定会解除，并恢复你最后一次手动选择的配置关卡。

### 为什么滚动关卡列表时会突然跳回去

元数据刷新不会再改变列表位置。展开列表时只会自动显示一次当前配置关卡；修改搜索时会回到第一条结果；使用键盘移动时只会显示键盘目标。除此之外，滚轮与滚动条位置始终由你控制。

### 为什么顶部猜单和真实菜单不一样

这是正常现象。
猜单不是“真实订单”，而是“有可能马上出现的参考候选”。

### 为什么画面看起来太拥挤

可以优先尝试：

- 不需要左侧面板时关闭 `显示悬浮窗`
- 降低 `最大猜单数量`
- 降低 `悬浮窗最大显示菜品数`
- 提高名称最大长度设置
- 调整悬浮窗位置

### DIY 关卡已经出现，但没有菜品

让设置窗口保持打开片刻以等待自动重试，或点击 `重试读取 DIY 菜谱` 立即重试。如果安装版本的接口不受支持，或某道菜无法完整预载，BepInEx 日志里会有一条 `[Compatibility]` 警告。

### 好像找不到某个 DIY 关卡

展开关卡选择器并搜索关卡 ID，例如 `s_rw_`。数量行会分别显示筛选结果、全部关卡和 DIY 关卡数量；OC2DIYLevel 状态行会说明元数据是已就绪、部分有效、仍在加载，还是正在沿用上一次有效快照。点击 `刷新` 会重新读取内存元数据。Menu Manager 不会退回到扫描 DIY 文件夹的方式。

### Recipe Extension 菜品没有出现

这些菜谱是在本局初始化时生成，不会提前出现在前端。确认 `OC2ManyRecipes` 1.1 已启用，开始新关卡并等待同步完成后再打开 `F6`。检查 BepInEx 日志中的一次性适配器就绪或兼容警告。当前关卡未使用的菜谱类别可以正常返回空数组；无效的非空数组会整体拒绝，不会显示容易误导的部分列表。

### 订单完成后仍显示在顶部

1.1.1 会在每张真实订单出现前预留有效的 UI 桌位，即使历史追踪已经关闭也会执行。同时会保护原版游戏没有边界检查的桌位释放逻辑，让已经在满 UI 中拿到无效桌号且成功交付的订单仍能正常播放动画并销毁。订单过期后保留并重置是 build 20236421 的原版行为。如果成功交付后仍残留，请保留 BepInEx 日志，并记录关卡名、当时的真实订单数量、Recipe Extension 选项和 `最大猜单数量`。

## 最简使用方法

如果你只想最快上手：

1. 安装 `OC2MenuManager.dll`
2. 启动游戏
3. 按 `F6`
4. 选择关卡
5. 勾选要追踪的菜
6. 打开 `启用菜单追踪`
7. 需要的话再打开 `显示悬浮窗`、`启用已备跟踪` 和 `菜单颜色`

这样就足够正常使用了。
